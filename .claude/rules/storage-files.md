# Object storage, uploads, Files RLS, and the same-origin XSS defense

Fires when you touch the Garage S3 client, per-tenant files, the tus upload server, the file-caps gate, the per-file prefix policy registry, or any byte-responder.

## Garage integration

Optional; activated by `GARAGE_S3_ENDPOINT` + friends in `.env`.

- **Garage is an independent service** (see `tool/garage/CLAUDE.md`). drust speaks plain S3 via `object_store::aws::AmazonS3`. drust boots with Garage unreachable — storage tab shows "not configured" / admin ops return 503; rest of drust unaffected.
- **Reads bypass drust.** Anonymous GETs hit Caddy `/public/*`, which reverse-proxies to Garage `s3_web` (`127.0.0.1:47831`) with `Host: public.web.local`. drust is only in the *write* path.
- **SQLite-first upload / S3-first delete.** Upload inserts metadata row, puts to Garage, compensates by deleting row on S3 failure. Delete calls Garage first (idempotent on NotFound), then clears row. Orphans surfaced by `reconcile` page.
- **`_system_*` drop-protected.** `storage::schema::is_protected_collection()` is consulted by `drop_collection`, for both admin-level `_system_files` and per-tenant `_system_files`.
- **Disk guard**: uploads return 507 when `/var/lib/garage` has less than `DRUST_DISK_MIN_FREE_PCT` (default 20) percent free.
- **Disk-guard scope (v1.59, GitHub #10)**: the guard and the admin disk panel read only the filesystem containing `disk_check_root()` — which is `data_dir` on a booted server (the `/var/lib/garage` string above is the unset-only fallback). Under the Helm chart's **default split topology** the object store is a **separate pod's PVC** that `statvfs` cannot reach, so the low-disk guard is **DB-filesystem-only by design** — a tenant can fill the object store without tripping it. v1.59 surfaces object-storage *usage* on the owner dashboard from `SUM(tenants.files_bytes)` (`build_object_store_view`, reporting only); an actual object-store low-disk *guard* (aggregate-quota or S3/Garage admin API) is deferred.
- **DR: the DB backup snapshot is not a self-contained recovery unit.** `backups.rs` `*.tar.zst` carries the SQLite DBs (and plaintext tokens) but **not** the object bytes, so a cold restore to an empty object store leaves `_system_files` rows dangling. Pair every DB snapshot with an object-store backup on every target: bare-metal `garage-backup.timer`, k3s `objectMirror` (Litestream covers databases only, not objects), docker-compose the `minio-data` volume.

## Per-tenant files

Tenant files live in two **host-wide** buckets — `public` (website-enabled, served via Caddy `/public/*`) and `private` (drust-proxied) — namespaced by a `<tenant-id>/` key prefix. Per-tenant buckets were retired; `_trash_pending_revokes` / `_orphan_buckets` + the `reconcile` page only clean up legacy per-tenant buckets left from before that change.

- **Cap-gated.** `src/tenant/file_caps.rs::file_caps_layer` (inner to `bearer_auth_layer` on `files_router`, replacing the older blanket `require_service_layer`) gates each route per-verb from a pure `classify_file_route` matrix: **service unrestricted; anon/user checked against the tenant's `file_anon_caps_json` / `file_user_caps_json`** (subset of `{read,list,upload,delete}`, default `'[]'` = service-only, so every existing tenant is unchanged). **make-public (`PATCH` set-visibility) + `sign` stay service-only** (not cap verbs). The cap is the OUTER of two gates — since v1.63 the prefix policy registry decides per FILE (see Files RLS below); the cap alone no longer means "every object in the tenant". Config service-only via MCP `set_file_caps` (auth-cache hook 12).
- **Dual-mounted verbs are split into two handlers, not one handler behind a permissive gate (v1.63).** `upload` / `stream_bytes` / `delete_one` are mounted on the data plane (behind `bearer_auth_layer`, so an `AuthCtx` exists) *and* under `/admin` (session cookie, no bearer, therefore **no** `AuthCtx`). The old rule here — "the gate MUST stay a layer, never a required handler extractor" — was written when the gate was cap-only; it is **superseded**, because reading "extension absent" as "service" is fail-OPEN the moment a per-file read gate hangs off it. Each verb is now `admin_tfiles_*` (admin twin, explicit bypass) + a data-plane handler over one shared `_inner`, and the data-plane side takes `RequiredAuthCtx` — a typed 500 `AUTH_CTX_MISSING` rather than a guess, matching the polarity of `file_caps_layer` / `require_service_layer`. Never relax it to an `Option`. Adding a fourth dual-mounted verb means adding a twin, not widening the extractor.
- The tus handlers keep an inline `require_file_cap` as DiD layer 2 **and bind each session to its creating bearer** (the `_system_upload_sessions.uploader` column records service/anon/`<user_id>`; a non-service `HEAD`/`PATCH`/`DELETE` whose identity ≠ `uploader` gets 404).
- **Visibility toggle** (`src/storage/visibility.rs::change_visibility`): public ⇄ private is a bucket move (copy → UPDATE row → delete-old), not a flag flip — the bytes physically move between the two buckets. Ordering keeps the live row always pointing at an existing object; a crash leaves a space-only reconcile orphan, retries are idempotent. The only UPDATE path on `_system_files`.

## Files RLS — the per-file gate (`src/storage/{file_policy,file_path}.rs`, v1.63)

The cap answers "may this caller do this VERB"; the registry answers "on THIS ROW". They AND.

- **`path` is metadata, not an address.** The Garage object key is still the server-minted flat `<uuid>.<ext>`, the route is still one segment, `/public/*` + signed URLs + `stream_bytes` are untouched. `_system_files.path` is a caller-DECLARED logical label (`avatars/alice/me.png`), used only for (a) prefix matching and (b) the admin page's fake folder tree. NULL = unfiled. It is **declared at upload and immutable** (no rename/move API; `change_visibility` does not touch it) and **not unique** — same path, many rows, deliberately: a uniqueness conflict would be an existence oracle for files the caller cannot see.
- **A folder is a prefix; the longest registered prefix wins.** `_system_file_policy` is one row per prefix (`prefix` PK, `''` = tenant root, anything else must end `/`), carrying `owner_scoped`, `public_read`, and optional `select` / `delete` `FilterAst` clauses. Longest match = inheritance + override with no tree, no folder objects, no rename problem. `delete` absent inherits the select semantics (readable ⇒ possibly deletable; the `Delete` cap is still the other half).
- **Two evaluators, one decision.** `authorize_file(policies, row_map, auth, access)` serves every single-file face (`get_one`, bytes, `delete_one`, edge `get-file`); `build_file_list_filter` compiles the same decision into the `list` `WHERE`. A change to either is a change to both — `tests/file_policy_expression.rs` is the invariant-12-style corpus (registries × callers × rows, SQL result set == in-memory set).
- **Prefix matching is a binary byte range**, `path >= ?p AND path < ?p⁺` with `p⁺` = last byte + 1 (`prefix_upper_bound`; a non-empty prefix ends `/` = 0x2F, so +1 never overflows). **Never `substr`** — SQLite counts CHARACTERS, Rust `len()` counts BYTES, so a CJK prefix arm never fires and the shorter looser arm wins: a silent fail-OPEN, measured. **Never `LIKE`** — `%`/`_` are ordinary path characters and SQLite's `LIKE` is case-insensitive. The range is byte-exact under BINARY collation and is served by `idx_system_files_path`.
- **Arm shape is a hard rule.** One arm per prefix, OR-ed, each subtracting the deeper prefixes under it; every fragment parenthesized and the whole group wrapped, never depending on operator precedence nor on `compile_policy_using` happening to emit an atomic fragment; the group is **never negated** (a `NOT` turns each Unknown into an admission). The root/default arm must spell out `path IS NULL OR NOT (…)` — `NOT (NULL >= ?)` is NULL, not TRUE, so omitting it silently drops every unfiled row. Binds are pushed in placeholder order and the clause is compiled BEFORE any bind is pushed, so a mid-arm refusal cannot desynchronize the whole statement.
- **Fail-closed, four ways.** No matching prefix ⇒ owner-scoped default (`uploader == $auth`, anon/service answer false). A clause-less row (`owner_scoped=0`, no select, `public_read=0`) DENIES — the write face refuses to create that shape (`FILE_POLICY_OPEN_REQUIRES_FLAG`) and the read face denies it anyway, so a legacy or hand-INSERTed row cannot read as "unrestricted" (the `select_read_access` lesson; the explicit-open decision lives in a COLUMN so it is structural, not a once-validated procedure). An unreadable registry or an unserializable row refuses. A file the policy hides answers **404**, not 403.
- **The engine is reused verbatim.** `file_policy_schema()` is a synthetic `CollectionSchema` for a file row, so `validate_policy` / `compile_policy_using` / `eval_policy` all apply with no second grammar. `content_disposition`, `cache_control` and `meta_json` are deliberately ABSENT from it (presentation, and JSON the `FilterAst` grammar cannot address). `id`/`created_at`/`updated_at` need no entry — the engine waves those three through unconditionally, which is exactly why `FileRow` carries `created_at`/`updated_at`: `eval_policy` reads the row map BY KEY and a missing key reads as Null, so an `updated_at is_null` clause on a short row map would match every file (fail-OPEN).
- **Connection discipline.** The policy read rides the connection the handler ALREADY opened — REST files handlers call `tenant_db::open_read` per request (they do not use the pool), MCP/edge use `pool.with_reader`. No second open, **no `get_or_create` on a read path** (it has resurrected soft-deleted tenants), and **no read-only authorizer** on these reads — it denies `_system_*` and would deny its own registry read. No cache, therefore no eviction invariant.
- **Service and the admin plane bypass** before the registry is even read, so a broken registry never locks a tenant out of its own recovery, and MCP's file tools need no RLS arm (`/t/<id>/mcp` is service-only by dispatch).
- **Upgrade seed.** Every pre-v1.63 row is `uploader='service'` with `path IS NULL`, so an unmatched-⇒-owner-scoped default would hide every existing file. Boot seeds each tenant `'' → public_read=1` (exactly today's "the cap is the only door"), guarded by the run-once `tenants.file_policy_seeded` marker: `run_migrations` runs on EVERY boot, so a bare `INSERT OR IGNORE` would resurrect a root policy an operator deliberately cleared. Tenants born after v1.63 are stamped at create (`make_tenant_inner`, which the id-recycle branch also reaches). Opting into deny-by-default = `DELETE /t/<id>/file-policies?prefix=`.
- **Surfaces.** REST `PUT` / `GET` / `DELETE /t/<id>/file-policies` (service-only on all three, list included — the registry IS the tenant's access map; the prefix rides a query parameter on DELETE because it contains `/` and the root is `""`, and an ABSENT parameter is a 400, never an implicit root clear). MCP `set_file_policy` / `list_file_policies` / `clear_file_policy` (tool count 73 → 76). Admin-plane twins `POST …/_files/policies` and `…/_files/policies/clear` exist because the service faces demand a service BEARER an admin session does not carry (the `admin_update_policies` precedent); the clear twin takes the prefix in a JSON body. All faces share `validate_file_policy` / `upsert_file_policy` / `delete_file_policy` — one kernel, so four surfaces cannot drift into four vocabularies. Error codes: `FILE_PATH_INVALID`, `FILE_POLICY_PREFIX_INVALID`, `FILE_POLICY_OPEN_REQUIRES_FLAG`, `FILE_POLICY_OPERAND_UNSUPPORTED`, `FILE_POLICY_NOT_FOUND`.
- **Path grammar is one choke point** (`storage::file_path::validate_file_path`): ≤512 bytes, segments 1–255 BYTES, no `.`/`..`/empty segment, no C0 or DEL, no leading or trailing `/`. Stored verbatim — no unicode normalization (NFC ≠ NFD are two paths), no trimming: the stored bytes are what a prefix rule is matched against, so a server-side rewrite would move a file into another folder's rules. Prefix validation is the same segment rule plus `''` and a mandatory trailing `/` (which is what stops `avatars` matching `avatarss/x`).

### The four upload stations (`enforce_upload_visibility` + `session_identity`)

Every station that writes a `_system_files` row makes the same three decisions, or the RLS above keys on a lie.

| Station | `path` | `uploader` | service default visibility |
|---|---|---|---|
| Mode-A multipart (data plane) | optional field, validated at the choke point | caller, via `session_identity` | `public` (historical, unchanged) |
| tus (`create` → finalize) | optional `Upload-Metadata: path`, carried on the session row | caller (already correct pre-v1.63) | **`private`** (historical, unchanged) |
| edge `put-file` | not accepted (WIT unchanged) ⇒ NULL | `function` when Privileged, else the caller | n/a — the WIT always sends a value, so there is no silent case; `put_file_raw` (Privileged) publishes unconditionally, `enforced_put_file` needs the ROOT rule's grant (v1.64) |
| host-admin `/admin/files/upload` → meta | optional, shared parser | `admin` | unchanged (management plane) |

- **The two service defaults differ on purpose.** Flipping tus to Mode-A's `public` would publish every existing service upload that omits the field; `tus_service_default_visibility_stays_private` exists to stop exactly that tidy-up.
- A **non-service** caller gets `private` when it says NOTHING — the half of v1.63 that stands, since pre-v1.63 Mode-A silently published every field-less upload. An **EXPLICIT** `public` from a non-service caller is gated by the per-prefix publish GRANT (v1.64, #974): `_system_file_policy.public_upload_roles` on the longest prefix rule matching the upload's declared `path` must name the caller's role (`anon` / `user`), else 403 / host-op `FILE_PUBLIC_UPLOAD_DENIED` — refused, never silently downgraded. So publishing AND-composes two gates exactly as reading does: the tenant-wide `upload` cap outside, the per-prefix rule inside. Deny-by-default, so the release grandfathers each existing tenant's ROOT rule once at boot (`seed_public_upload_grant`, marker `tenants.public_upload_seeded`). Station inputs: Mode-A and tus pass the declared `path` (tus decides at CREATE and freezes it on the session — the create→finalize rule-change race is accepted and documented in the handler); the edge station declares no path at all, so only the root rule `''` can grant it. Each station pre-fetches the registry on the connection it already holds, gated on `files::publish_grant_lookup_required` — the decision's own predicate, because the decision's loader is sync and the pools are async. Two earlier shapes were replaced and neither shipped: v1.63.0's blanket `FILE_VISIBILITY_SERVICE_ONLY` refusal (deleted) and v1.63.1's "explicit is always honored". `sign` and set-visibility stay service-only regardless (CLAUDE.md invariant 19).
- The uploader sentinels (`service` / `anon` / `function` / `admin`) cannot collide with a real user id — user ids are always server-minted `u-<uuid>` and no caller picks its own — so `uploader == $auth` is unspoofable.

## Mode B large-file upload / tus 1.0 (`src/tenant/uploads/`)

Resumable-upload server at `/t/<id>/uploads/*`: five tus methods plus a service-only `GET` (list sessions), all cap-gated per verb like Mode A. Each `PATCH` chunk is bounded by `DRUST_LARGE_UPLOAD_CHUNK_MAX_BYTES` (default 64 MiB) via a per-route `DefaultBodyLimit`; chunks append to a durable spool file (`tenants/<id>/_uploads/<token>.part`) so the filesystem byte-count is the offset source of truth and resume survives client disconnect and server restart. On completion: `INSERT OR IGNORE` a `_system_files` row (SQLite-first, idempotent) carrying the `path` declared at `create` and parked on `_system_upload_sessions.path`, stream the spool to Garage via `put_file_in`, then delete the spool and session row. Hourly in-process janitor reclaims abandoned sessions; never touches `_system_files` or Garage.

> [!WARNING]
> **Mode B keeps every HTTP request small by design (chunks ≤ `DRUST_LARGE_UPLOAD_CHUNK_MAX_BYTES`, default 64 MiB) so it stays under the 200 MB Caddy/.221 ingress limit.** Never raise a body-limit to accommodate large uploads — the tus chunking protocol exists precisely so each individual request stays small.

## Stored-XSS mitigation (`src/storage/files.rs`)

Tenant bytes are served from the **same origin as the admin UI** (Caddy serves `/public/*` and `/drust/*` from one site block), so a caller-supplied `text/html`/XML content type rendered `inline` executes script in the admin plane's origin — escalating a tenant service key to host-admin.

The fix sandboxes the *rendering*; the declared type is kept as-is. Ingest only lowercases the essence via `normalize_content_type_case` — MIME matching is case-insensitive so this changes nothing about how any client renders the file; it exists solely so the case-sensitive Caddy layer below only needs to match one canonical casing. `storage::files::insert_content_type_headers` — the ONE function all three drust byte responders (`tenant_files::stream_bytes`, admin `/admin/files/{key}/bytes`, `signed_bytes::respond`) call — sends `Content-Security-Policy: sandbox allow-top-navigation-by-user-activation` (`SANDBOX_CSP`) whenever `is_unsafe_inline_type` flags the stored type. Bare `sandbox` gives the document a unique opaque origin and disables scripts/forms/popups; `allow-top-navigation-by-user-activation` restores plain hyperlink clicks without re-enabling anything script-driven — the same technique GitHub uses for `raw.githubusercontent.com`.

> [!CAUTION]
> **`allow-same-origin` and `allow-scripts` must NEVER be added to `SANDBOX_CSP`** — either one defeats the protection; a codified test pins the exact string. The classifier stays **structural, not an enumeration** — every `<type>/<subtype>+xml` essence is an XML document type to Blink/Gecko (the first version of this fix was broken by `application/rss+xml`). `nosniff` remains unconditional on every responder — the orthogonal defense against a browser sniffing a *different* declared-safe type back into HTML. **ANY new byte-responder path MUST call `insert_content_type_headers`.**

The Caddy `/public/*` block (which bypasses drust entirely, reverse-proxying straight to Garage) carries a matching `handle_response` matcher keyed off the upstream's own served `Content-Type` — never the request path's extension, which a caller sets independently of the declared type. Caddy 2.6.2's response-matcher allowlist has **no regex or case-insensitive option**, only a plain glob on `header`, so the matcher is a boundary-aware exact + prefix-with-`;` pair per essence (never a loose `text/html*`, which would also flag `text/html-ish`) and depends on drust's lowercase normalization above.

> [!WARNING]
> **Changing `is_unsafe_inline_type` obliges you to change the Caddy `@markup` matcher in the same breath**, and to verify it live rather than trusting `caddy adapt`. The matcher lives in `../garage/deploy/Caddyfile`; the `copy_response` rule that governs any edit to that block is in `.claude/rules/build-deploy.md`, which has the full outage story.

**Stored strings never reach a header via `.parse().unwrap()`** — tus takes `Upload-Metadata: filetype` as unvalidated free text, so `safe_header_value` degrades instead of panicking the responder.
