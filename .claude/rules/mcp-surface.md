# MCP protocol surface

Fires when you open the MCP server: the account-level endpoint, tool dispatch, resources, prompts, or the MCP registry.

## Transport & gate

**One account-level MCP endpoint** at `<base>/mcp` — rmcp Streamable HTTP in stateless mode (`account_routes::account_http_config`: `with_stateful_mode(false)`, `NeverSessionManager`, SSE responses with a 15 s keep-alive), so there is no session id and no GET stream. In front of rmcp, in order: `mcp_route_layer` (404 `MCP_DISABLED` while `DRUST_MCP` is not enabled, 421 `MCP_HOST_NOT_ALLOWED` for a Host outside `allowed_hosts()`, 403 `MCP_ORIGIN_NOT_ALLOWED` for a disallowed browser `Origin`, 413 `MCP_BODY_TOO_LARGE` for a declared `Content-Length` over 16 MiB, `X-Accel-Buffering: no` on an event stream), `mcp_oauth_auth_layer` (auth-tenancy.md), then `mcp_body_buffer`, which cuts a chunked body at 16 MiB with the same 413 — after authentication. The handler is `account::AccountMcp`: `tools/list` is the 76 inner tools plus `list_tenants` and `create_upload_url` (`AccountMcp::tool_count()`, 78), and every tool except `list_tenants` takes a required `tenant` argument, put first in its inputSchema by `inject_tenant`. `call_tool` rejects a top-level argument the inputSchema does not list with `INVALID_ARGUMENTS`, resolves the tenant through `resolve_tenant` (CLAUDE.md invariants 7 and 21), builds a fresh `DrustMcp` through `McpRegistry::build_live` and forwards to the inner tool; `finish_account_call` turns every remaining JSON-RPC error except "tool not found" into an `isError` result. A refusal before the tenant is opened (`precheck`, `resolve_tenant`) and `create_upload_url` build their `isError` result themselves and do not pass through it; `list_tenants` does. The caller acts as Service on that tenant with the grant's admin id; `whoami` returns the tenant's identity, the anon key, a redacted service key (`redacted`, `id`, `created_at`, `how_to_get`) and the REST and upload paths.

The inner `#[tool]` router in `src/mcp/handler.rs` holds every tenant tool; `AccountMcp::call_tool` forwards to it (`DrustMcpService::tool_router()`) with the request's `RequestContext`, and therefore the peer, so pushing from a tool, resource or prompt handler is server push (invariant 5). `DrustMcpService`'s own `ServerHandler` impl (a hand-written `call_tool`, so `#[tool_handler]` generates only `list_tools` / `get_tool`) is not mounted on any route. `McpRegistry` keeps its per-tenant `DrustMcp` cache (`get_or_create`), which the account endpoint never reads or writes and no production code fills (`get_or_create_has_no_production_caller_outside_this_file`); `McpHttpRegistry::evict` clears it on soft-delete and on an id-recycling create (`evict_tenant_everywhere`). An old-incarnation pool must close BEFORE the id's new database is in use: SQLite unlinks `-wal`/`-shm` by path when a pool's last connection closes. **Never run `rmcp` at `debug` or `trace`** (`RUST_LOG` replaces the default `info,drust=debug,tower_http=info` filter as a whole): rmcp then logs whole MCP requests and results, upload tickets included.

`call_rpc` stays on the read-only executor regardless of the RPC's stored `mode`, so REST, the admin playground, and cron fires are the only write-RPC execution surfaces. MCP `call_rpc` always runs as the endpoint's Service caller (the per-RPC `anon_callable` flag gates only the anon REST path); a `kind='query'` RPC runs under `service_ctx()` with the admin id.

## Resources & Prompts

`src/mcp/{resources,prompts}.rs` — hand-written `ServerHandler` methods; **rmcp has no resource/prompt macro**. Read surface only. On the account endpoint `resources/list` is empty on purpose and `resources/templates/list` lists every resource as a `drust://{tenant}/…` template (`account_resource_template_list`: the 10 static paths plus the 4 templates below); `list_tenants` carries each tenant's `schema.md` URI. `read_resource` takes the tenant from the URI's host and runs `resolve_tenant` on it before anything is parsed against it; the per-tenant `parse_resource_uri` then checks the host again. Resources address tenant knowledge as `drust://<tenant>/<path>`: 10 static (`schema`, `schema.md`, `collections`, `openapi.json`, `types.ts`, `zod.ts`, `functions`, `rpcs`, `cron`) thin-routing to the existing `get_schema_overview`/codegen/inventory readers, plus **`files-guide.md`** — the one static resource that is AUTHORED rather than projected: a Markdown guide to uploading through a `create_upload_url` ticket, the public/private model and the per-prefix publish grant, with this tenant's live `public_upload_roles` list appended at read time. It carries no credentials by the rule below. The `whoami` TOOL carries the anon key and a redacted reference to the service key, and points at the guide through a two-key `file_upload` block — deliberately a signpost, since the alternative was a `whoami` that grows a paragraph per feature. `mcp::tools::file_policy::public_upload_grants` is the ONE grant lister both surfaces call. Plus 4 templates (`collections/{collection}/schema`, `collections/{collection}/records{?page,per_page,sort,order}`, `collections/{collection}/records/{id}`, `rpcs/{name}`).

> [!CAUTION]
> **A resource is auto-fetchable into model context (spec §3), unlike a tool that needs an explicit call** — so anything credential-bearing must stay behind a TOOL. `rpcs`/`rpcs/{name}` strip RPC `sql` + param `default`; `cron` strips `payload_json` **and `last_error`** (rusqlite's `SqlInputError` `Display` embeds the whole failing statement, so a prepare-failing RPC cron job would publish through `cron` the very SQL the `rpcs` resource strips — `redact_cron` replaces it with a `last_error_present` boolean, and the full text stays behind the `list_cron_jobs` TOOL); the `history` + `functions/{name}/logs` templates are **deliberately NOT exposed as resources** (old-row snapshots / function stdout can carry secrets — they stay behind the `get_record_history` / `get_function_logs` TOOLS).

**URI parser** (`parse_resource_uri`) is a SINGLE `url::Url::parse` + deny-by-default: authority gate + `as_str()==raw` (rejects every url normalization incl. literal AND `%2e`-encoded dot-segments) + no-`%` segments + per-route query hardening (reject `%`/`+`/duplicate/unknown query keys — `query_pairs()` form-decodes past `as_str()==raw`, e.g. `?p%61ge=2`→`page`); **cross-tenant guard is `host_str()==tenant_id`**; `{c}` runs the `identifier` + `is_protected_collection` gate; `{id}` is a canonical i64 (rejects `/records/05`).

`Record{c,id}` uses a **dedicated bound-i64 single-row reader** (the `/list` filter validator only accepts declared fields, so an id-filter is `FILTER_UNKNOWN_FIELD`).

Bodies capped at `DRUST_MCP_RESOURCE_MAX_BYTES` (default 256 KiB, UTF-8-boundary truncation + marker); one `mcp.resource.read` audit row in the tenant per successful read; a refused read (missing, invisible or malformed tenant) writes one host-level `mcp_denied` row. A read that passed the tenant check and then fails writes nothing: a URI that fails to parse, a missing record, an internal error. A rendered prompt writes no row (it only reads schema); a prompt refused at the tenant check writes a host row, and a failure after that check (an unknown prompt name, a `secure_collection` collection that does not exist) writes none. Host rows use `tenant = "-"` (`tenant_db::HOST_AUDIT_KEY`), a reserved tenant id: `validate_tenant_id` refuses it, so no tenant can be created with it. A tenant named `-` created by an older release keeps its data plane, but its per-tenant log page and JSON answer 404 (the host rows are never shown there), its overview, room-eviction and broadcast-inspector routes answer 400, this endpoint answers it like a missing tenant and leaves it out of `list_tenants`, and every boot logs one warning naming it; it cannot be renamed, only deleted. rmcp logs every error response at WARN, so a resource or prompt error never echoes caller text unbounded: the URI goes through `account_audit::shown_uri` (the shape-checked URI or `<invalid>`, cut to `URI_MAX_CHARS`) and a collection or prompt name through `shown_name`; an internal error from the records template answers only its classified code.

> [!WARNING]
> Read TOOLS carry a **top-level** `resource_link` (concrete on `insert_record`) / `resource_uri_template` (on `list_records` + `search_collection`) — **never per-row**: the default projection omits `id`, and `resource_link` is a legal user column name.

**Prompts** (`prompts/list` + `prompts/get`): 6 task recipes — `bootstrap` (embeds the live `schema.md` + core rules), `design_collection{purpose}`, `secure_collection{collection}` (embeds `describe_collection`), `debug_write{collection}`, `write_edge_function{trigger}`, `review_history{collection}`; bodies mirror existing service tools (no new exposure), unknown/missing-arg → `-32602`. On the account endpoint every prompt takes a required `tenant` argument first (`prompts::account_prompt_list`); `get_prompt` runs `resolve_tenant` on it before rendering, and a missing or invisible tenant is `-32602` with `error_code` `TENANT_REQUIRED` / `TENANT_NOT_FOUND`. In Claude Code a prompt is a user slash command, not something the model can call — so the instructions name prompts as recipes to suggest, and anything the model itself needs (e.g. that edge functions are deployed from the admin UI, never through this connection) must also be in the instructions or a tool description.

Capabilities declare `resources` + `prompts` but **`listChanged` is NOT declared** (the full capability set is pinned by `server_capabilities_declare_no_server_push`, and `mcp_sources_never_push` fails on any `src/mcp/` code naming the peer, since rmcp does not stop an undeclared push; see CLAUDE.md invariant 5) — `resources/list_changed` notifications and subscriptions are deferred: both need a per-tenant schema-change notification bus + live MCP-peer subscription; the `#[tool]` handlers don't receive the peer, and schema also mutates from REST/admin faces — disproportionate infra for a re-listable convenience.

## Server instructions and tool annotations

**Instructions** (`ACCOUNT_INSTRUCTIONS` in `src/mcp/account.rs`, served as `initialize.instructions`): one fixed text that **must** stay ≤ `INSTRUCTIONS_MAX_CHARS` (4,096 — Claude Code's cap, and what it reads to decide whether to search this server's tools at all); `get_info` carries a `debug_assert!` and `account_instructions_fit_the_cap` pins it. The text is close to the cap: measure before adding a word. The rules that prevent damage come first; every tool is named at least once, as a whole word (`account_instructions_name_every_tool`); URLs, credentials and tenant ids never appear in it; long detail lives in tool descriptions, the `files-guide.md` resource or the prompts.

**Annotations**: the source of truth is `annotation_tests::TABLE` in `src/mcp/handler.rs` — `readOnlyHint` and `openWorldHint` are written out on every tool; `destructiveHint` and `idempotentHint` only on non-read-only tools (a `Read` row leaves them unset, and rmcp omits an unset hint from the wire, so the 26 read-only tools carry neither). Claude Code automatically re-sends, after a dropped connection, any tool whose `readOnlyHint` **or** `idempotentHint` is true. So a TABLE `Read` row must truly not write (bookkeeping-only writes excepted, e.g. `call_rpc`'s call counter — those go in `RETRY_SAFE_WRITES`), and every idempotent write must be listed in `RETRY_SAFE_WRITES` with its reason. The test can only compare TABLE against that list; it cannot catch a `Read` row that actually writes — that is the job of reviewing TABLE. A record write that fans out (`update_record`, `upsert_records`, …: webhooks, edge functions, realtime events, record history) is never idempotent. `openWorldHint` is true only on `invoke_function`. A new tool needs a TABLE row and its name in the instructions' TOOL GROUPS.

## AI introspection helpers

Every REST error JSON includes a `suggested_fix` field with a context-aware remediation hint; same on MCP when the code is catalogued: in `ErrorData.data` on every JSON-RPC tool error (`bail_mcp`, plus the `call_tool` backstop `ensure_error_code`; the code is decided by `mcp::error_code::mcp_error_code`: leading `CODE:`, else a closed-set sentinel directly after `PrepareError`'s prefix, else the ordered needle table, else `INVALID_PARAMS` / `INTERNAL` — every step but the first returns a table constant; the first returns the message's own leading token, which is drust's prefix only while no message starts with caller text — pinned for the tool-module literals, not for verbatim `Display` / `e.to_string()` forwards), and in the JSON text of an `isError: true` result for the five tools that report failure as a sentinel object (`describe_collection`, `delete_record`, `delete_file`, `get_file_url`, `set_file_visibility`, plus `list_files`'s `INVALID_VISIBILITY`) and, on any tool, an argument that fails to deserialize (`INVALID_PARAMS`, `finish_tool_call` — rmcp ≥ 1.8 would otherwise answer its own plain-text isError). The conversion is `handler.rs::sentinel_or_json` → `tool_error`, wrapper-level only: the inner fns keep their `Ok({"error_code"})` shape because edge (`write::delete_record`), resources and prompts (`exploration::describe_collection`) read it. Never route a data-returning tool through `sentinel_or_json` — a user column may be named `error_code`. New tool code should still bail `"<CODE>: <message>"`; the classifier is the backstop, and `every_unprefixed_tool_literal_has_a_code` fails on a literal it cannot classify. Do not add a `suggested_fix` for a code REST also emits (e.g. `TYPE_MISMATCH`) without checking every REST use — `json_error` attaches it there too. `create_rpc` / `update_rpc` / `call_rpc` set their codes at the site (`prepare::save_error_code`, `RegistryError::save_code`, `ParamError::code`, `ExecError::code` — the last two shared with REST's RPC handler). Catalog of fixes in `src/safety/error_fixes.rs`; blast-radius probes in `src/storage/blast_radius.rs`. A caller of the account-level endpoint sees the JSON-RPC form only where drust neither ran nor refused the call: an unknown tool ("tool not found"), a task-augmented call, and a request the transport cannot parse (an HTTP error from rmcp). Everywhere else `account::finish_account_call` runs `finish_tool_call` and then turns every JSON-RPC tool error into the same `isError: true` body, keeping its `error_code` (classified by `mcp_error_code` when the error carries none) and `suggested_fix`, and the refusals before the tenant is opened are built in that shape directly. The shapes above are the inner tools' own, which edge functions, resources and prompts depend on.

Only `delete_record` / `drop_collection` / `drop_index` have `dry_run`; every other tool rejects a `dry_run` argument with `INVALID_ARGUMENTS`, because the account endpoint's `call_tool` rejects any top-level argument its inputSchema does not list (the inner `*Args` structs still have no `deny_unknown_fields`). `account_instructions_dry_run_claims_match_the_schemas` ties the instructions sentence to the inputSchemas. These three destructive ops accept `dry_run: true` and return `would_*` counts + blast radius without mutating. A real `drop_collection` also closes that collection's SSE subscriptions and may return `warnings` naming dependent anon-callable RPCs; `dry_run` does neither. `drop_field` may likewise return `warnings` (`FIELD_REFERENCED_BY_POLICY`, one per stored policy clause still naming the dropped field); it neither refuses nor evicts.

`recent_writes` reads mutation rows from `meta_logs.sqlite` filtered to the calling tenant by tool-name `op`. The account endpoint writes one row per tool call that passed its tenant check: `op` = the tool name (`<tool>.dry_run` for a `dry_run: true` call, so a preview never reads as a write), the collection in `extra.collection` (`create_collection` takes it from `name`), `auth_method = "mcp_oauth"` and the admin in `actor_admin_id`. Only the ops in `safety::recent_writes::WRITE_OPS` are listed: the record writes, `call_rpc`, and the six schema operations `create_collection` / `drop_collection`, `add_field` / `drop_field`, `create_index` / `drop_index`; other schema changes (policies, caps, `owner_field`, descriptions, full-text indexes), a `.dry_run` row, and writes made through REST or the admin UI are not. The description and instructions recommend it before re-sending a write whose reply was lost, and the `debug_write` prompt checks it first, then `list_records`, reading a failure from the `isError` result. Default limit is **100** (pinned by `tests/mcp_recent_writes_limit.rs`); an explicit `limit` wins and is clamped to `1..=200`.

> [!CAUTION]
> **A `///` doc comment on any `*Args` field in `src/mcp/handler.rs` is model-facing, not prose.** Those structs derive `schemars::JsonSchema`, so each doc comment is published verbatim as that property's `description` in the `tools/list` inputSchema — the surface the prologue itself designates canonical and that most MCP clients render into the system prompt. Changing a default or a range in the handler body means changing the doc comment in the same commit; a prose-only sweep leaves the machine-readable number stale and the model holding two answers. `tests/mcp_recent_writes_limit.rs` pins this for `recent_writes`.

## FilterAst arguments (`filter` / `using` / `check` / `where`)

Every structured-filter argument — `list_records.filter`, `aggregate.filter`, `search_collection.where`, `set_policy.using`/`check` — is typed `Option<serde_json::Value>` and parsed through the single `crate::query::vector_filter::parse_filter_value`, never a bare `serde_json::from_value`. That helper tolerates a **double-encoded JSON string** (many MCP clients stringify object-typed arguments) by decoding one layer, and on failure returns `filter_shape_hint()` instead of serde's opaque "did not match any variant of untagged enum FilterAst". A new filter entry point MUST route through it, and each field carries `#[schemars(schema_with = "…::filter_arg_json_schema")]` so the advertised inputSchema is an `object`, not schemars' untyped "any" (which is what invited the stringifying).

> [!CAUTION]
> **The wire shape is `{field: scalar}` / `{field: {op: operand}}` / `{and|or|not}` — NOT `{op, field, value}`.** Operators: eq, ne, gt, gte, lt, lte, like, in, nin, is_null, is_not_null (`ne`, not `neq`). `src/codegen/filter_ast_schema.rs` (OpenAPI/TS/Zod) once described the `{op,field,value}` shape the parser never accepted, so every generated client built filters that always failed and the golden fixtures pinned the lie. Two guard tests keep the two sides honest: `src/query/vector_filter.rs::documented_shapes_match_the_real_parser` compiles the documented examples against the real compiler (parser side), and `src/codegen/filter_ast_schema.rs::codegen_ops_match_parser_and_drop_the_drifted_shape` asserts the operator names in every renderer match the parser's and that `neq` / the `{op,field,value}` keys are gone (codegen side). Neither cross-validates the generated JSON-Schema against the Rust parser end-to-end, so a change touching both still needs eyes.
